# 图片处理功能架构分析与优化方案

> 分析日期：2026-10-13
> 基线：`v2.0.0-beta.18`（含 2026-10-12 审计全部修复）
> 范围：`processQueue` / `backfillThumbs` / 缩略图生成 / 临时文件生命周期 / 并发模型
> 方法：静态代码审计 + 逐条复核（所有结论均标注 file:line，可自行验证）

---

## 0. 结论速览

现有管线的**设计质量高于同类项目平均水平**——条件认领、陈旧窗口、失败回滚、
守卫式 UPDATE 都做得相当扎实。但存在**一个架构级限制**和**三处确定性资源泄漏**：

| 类别 | 数量 | 说明 |
|---|---|---|
| 🔴 架构级限制 | 1 | **浏览器即 worker**，无后台进程；关页面即停摆 |
| 🔴 确定性资源泄漏 | 3 | 临时文件泄漏 2 处、前端紧循环 1 处 |
| 🟡 正确性缺陷 | 1 | 内存预检的批内顺序依赖（大图被误判跳过） |
| 🟡 规模化瓶颈 | 2 | 每请求 8 次 COUNT（2 次全表回表）、批次上限硬编码 10 |
| 🟢 整洁度 | 3 | 驱动实例未复用、`SELECT *`、3 处状态写入重复 |

**先修 3 个 P0（都是小改动、影响真实）**，再做规模化优化。
架构改造（后台 worker）建议单独立项——它是唯一能改变量级的能力。

## 1. 现有架构

### 1.1 数据流

```
上传 → 落盘 storage/incoming/{yyyy}/{mm}/{uuid}/original.ext
     → INSERT images (process_status='pending', url='', thumbs=NULL)
     → 前端轮询 POST /admin/images/process-queue (batch=10)
        ├─ 开头：5 分钟陈旧窗口复位（processing → pending）
        ├─ SELECT * ... WHERE pending ORDER BY id LIMIT n
        ├─ 条件 UPDATE 认领：WHERE id IN(...) AND process_status='pending'
        └─ 逐图：上传原图 → 解码 → 生成 sm/md/lg → 逐档上传 → 置 done → 删临时
     → 循环直到 remaining === 0
```

### 1.2 状态机

```
pending ──条件UPDATE认领──> processing ──┬──成功──> done
   ↑                                     │
   └──── 5min 陈旧窗口复位 ───────────────┴──异常──> failed ──requeue──> pending
```

并发控制靠**条件 UPDATE 的 rowCount 互斥**（`ImageController.php:847-863`），
而非锁。这是正确且低开销的做法。

### 1.3 做得好的地方（应保留）

- **条件认领替代锁**：并发安全但无锁开销，失败时自然放弃本批
- **守卫式 UPDATE**：`WHERE ... AND process_status='processing'`（`:946`）——
  并发方已落定时 `rowCount=0`，不覆盖权威状态
- **失败回滚已落桶对象**（`:973-1000`）并把残留 key 写审计 —— 避免了孤儿泄漏
- **补全不改 `process_status`**（`:1055` 注释）—— 否则存量图会因前台过滤全部下架
- **零逻辑重复**：`processQueue` 与 `backfillThumbs` 共用同一批 helper
  （`makeThumbnails` / `uploadThumbs` / `discardThumbs` / `deriveThumbMeta`），
  CLI 脚本也复用控制器方法。这是本次审计中最值得肯定的设计

## 2. 问题清单（按优先级）

### P0-1 🔴 backfill 路径泄漏完整原图副本

**位置**：`ImageController.php:1252-1263`

```php
$localFile = S3Driver::downloadUrl($driver->url($path));  // 完整原图落 sys_get_temp_dir()
if ($localFile === null) { throw ...; }
$isTemp = true;
$gen = $this->makeThumbnails($localFile, ...);   // ← 抛异常则下面不可达
if ($isTemp) { @unlink($localFile); }             // ← 永远到不了
```

`$localFile` 是循环内局部变量，异常展开后引用丢失，外层 `catch`（`:1305`）
**不知道它的存在**。每次对象存储侧硬失败（原图取不到、存储不可达、OOM）
都永久泄漏一份完整原图到系统临时目录。

`cleanupStagingFiles`（`:1879`）只扫 `incomingDir()`，**不覆盖 `sys_get_temp_dir()`**。

> **影响**：反复触发即可填满 `/tmp`。这是本次最严重的一处。

---

### P0-2 🔴 缩略图临时文件泄漏

**位置**：`ImageController.php:619-633`

```php
$tmp = tempnam(sys_get_temp_dir(), 'moerng-thumb-' . $size . '-');
$ok = imagewebp($dst, $tmp, $quality);
// ...
$out[$size] = [
    'tmp' => $tmp,
    'key' => \App\Models\Image::thumbKey($size, $path),  // ← 可抛
    'bytes' => ...,
];
```

`Image::thumbKey()`（`Image.php:120-129`）对**历史 v1 布局**的 path 抛
`RuntimeException`。抛出时：

- 当前档的 `$tmp` 尚未进入 `$out`（赋值未完成）
- `$out` 里已累积的 sm/md 条目随栈帧销毁丢失
- 调用方 `$gen` **仍是 `null`**（`:875`/`:1166` 在 try 外声明）
- → `discardThumbs(null)` 在 `:669` 直接 return，**一个文件都不删**

> **影响**：`processQueue` 不受影响（只处理新上传的 v2 布局）；
> `backfillThumbs` 受影响（`:1157` 取 done 行，含 legacy 存量）。

---

### P0-3 🔴 前端紧循环（多管理员场景下的自我压测）

**位置**：`app.js:1414-1419` + `ImageController.php:852-861`

认领失败时服务端返回 `done=0, failed=0, remaining>0`。前端：

```js
if (remaining === 0) break;                    // 不触发
if (nDone === 0 && nFailed > 0) throw ...;     // nFailed=0，不触发
// → 立即重新 POST，无任何退避
```

两个管理员同时轮询时，输家进入**以网络 RTT 为间隔的无限循环**，每次迭代 = 
1 个 HTTP 请求 + **8 条 COUNT（其中 2 次全表回表）**。

> 恰好把 §3.2 的全表扫描打成持续压测，且表越大越严重——正反馈恶化。

---

### P1-1 🟡 内存预检的批内顺序依赖

**位置**：`ImageController.php:560`

```php
$available = $limit - memory_get_usage(true) - self::MEMORY_BASELINE_HEADROOM;
```

用 `memory_get_usage(true)`（real_size，含分配器已向系统申请的内存）。
PHP 分配器在请求内**释放内存只还给自己的 free list，不还给操作系统**，
故 `real_size` 在一个请求内**单调不减**。

后果：同一批次内，靠后的图片 `available` 被前面图片撑起的峰值压低 →
本该放得下的图被判 `too-large`（`:589`）而**静默跳过缩略图**。

> 同一批图片换个顺序，结果就不同。单张检查是安全的，批量复用同一基线就不安全。

---

### P1-2 🟡 每请求 8 次 COUNT，其中 2 次全表回表

**位置**：`ImageController.php:820-1032`

| 位置 | 语句 | 代价 |
|---|---|---|
| `:820` | `COUNT(*) FROM images` | O(N)，但选的是最小索引 |
| `:1027` | `COUNT(*) WHERE 'done'` | 范围扫描，可接受 |
| **`:1029`** | `done AND <JSON 谓词>` | **≈N 次回表 + JSON 解析** |
| **`:1032`** | `done AND <JSON 谓词>` | **同上** |
| `:821`/`:1012`/`:1015`/`:1026` | 按状态范围扫描 | 便宜（pending/failed 通常很小） |

关键在 `Image::thumbMetaPendingSql()`（`Image.php:343-348`）：

```sql
COALESCE(JSON_UNQUOTE(JSON_EXTRACT(IF(JSON_VALID(processing_state),
  processing_state), '$.thumb_meta')), 'pending') = 'pending'
```

`idx_process_status(process_status)` 单列索引只能服务 `process_status='done'`
这一个等值条件；`processing_state` 不在任何索引中，且谓词含 `JSON_VALID`/
`JSON_EXTRACT` **非 sargable**，无法转索引查找。

> 10 万张图 95% 是 done 时 = 约 95000 次回表，**每个批次轮询一次**。

---

### P1-3 🟡 批次上限 10 硬编码 5 处

| 位置 | 代码 |
|---|---|
| `ImageController.php:792` | `max(1, min(10, ...))` |
| `ImageController.php:1064` | 同上（backfill） |
| `app.js:1362` | `const BATCH = 10;` |
| `cli/backfill-thumbs.php:31` | `max(1, min(10, ...))` |
| `cli/backfill-thumbs-batch.php:20` | `max(1, min(10, ...))` |

每请求固定成本（11 条查询）被摊到只有 10 张图上。10 万张 = 10000 次请求 ×
4 次全表扫描。提到 50–100 可把这部分开销降 5–10 倍。

### P2 级（整洁度，不影响正确性）

| 问题 | 位置 | 说明 |
|---|---|---|
| 驱动实例未复用 | `:895`、`:1195` | 用 `$profile->driver()` 而非 `StorageProfile::cachedDriver()`（`:74`），每张图重建驱动 → **N 次凭据解密**（每 profile 2 个 secret 即 20 次对称解密）+ N 次 `realpath` |
| `SELECT *` | `:831`、`:1157` | `processQueue` 路径浪费较小（pending 行大列恒 NULL），但 `backfillThumbs` 取 done 行，`url`(1024) / `original_name` / `file_hash` / `file_sha256` / `process_error` 纯浪费 |
| 3 处状态写入块重复 | `:941`、`:1222`、`:1276` | 近乎相同；`stampThumbMetaState()` 已存在但只用了 1 处，另两处内联重造 `withProcessingState(...)` |

### 架构级 🔴 没有后台 worker

**确认**：`grep processQueue src/cli/` **无命中**。`src/cli/` 只有
`backfill-thumbs.php` / `backfill-thumbs-batch.php` / `migrate-apikey-hash.php`。
全项目无 cron / systemd / supervisor / daemon。

`app.js:1316-1320` 注释确认设计意图：*"移除「页面加载静默清队列积压」的自动触发。
处理队列只在两个时机消费：① 上传批次完成后自动跑一次；② 用户手动触发"*

> **浏览器就是 worker。** 关闭标签页 = 完全停摆；无人操作 = 积压永不消费。

**吞吐估算**（推断，需实测）：单图 0.3–1.5 s（GD 单线程 libwebp q82），
批次 10 张 = 3–15 s/请求 → **理论上限约 0.7–3.3 图/秒**。
清空 10 万张积压 ≈ **22 小时**（单管理员）。

## 3. 优化方案

### 3.1 第一批：修 3 个 P0（小改动、无破坏性、可独立验证）

#### ① `makeThumbnails` 内部自清理

把临时文件的所有权交给函数自己——用 `try/finally` 包住生成循环，
异常时清理已落盘的 `$tmp`：

```php
$out = [];
try {
    foreach ($sizes as $size) {
        $tmp = tempnam(sys_get_temp_dir(), 'moerng-thumb-' . $size . '-');
        // ...
        $out[$size] = ['tmp' => $tmp, 'key' => ..., 'bytes' => ...];
    }
    return ['readable' => true, 'thumbs' => $out, 'reason' => 'ok'];
} catch (\Throwable $e) {
    foreach ($out as $t) { if (!empty($t['tmp'])) @unlink($t['tmp']); }
    throw $e;
}
```

**收益**：无论调用方怎么写，临时文件都不会泄漏。调用方的
`discardThumbs` 保留（成功路径仍需要它）。

#### ② `backfillThumbs` 把下载文件提到 try 外

```php
$localFile = null;
$isTemp = false;
try {
    // ... 下载 ...
    $localFile = ...; $isTemp = true;
    $gen = $this->makeThumbnails($localFile, ...);
} finally {
    if ($isTemp && $localFile !== null) @unlink($localFile);
}
```

或者更稳妥：在 `backfillThumbs` 的外层 catch 里加一个
`finally { if (isset($localFile) && $isTemp) @unlink($localFile); }`。
两者选一，**推荐 `finally`**——它对所有退出路径都生效。

#### ③ 前端紧循环退避

服务端在「认领失败且 remaining>0」时返回 `contended: true`：

```php
if ($marked !== count($ids)) {
    $this->json([..., 'contended' => true, 'remaining' => ...]);
    return;
}
```

前端：

```js
if (j.contended) { await new Promise(r => setTimeout(r, 800 + Math.random() * 400)); }
```

带抖动的固定退避即可。**不需要指数退避**——认领失败通常 1–2 次就成功。

**验证**：三处改动均可由现有 harness 覆盖，建议补断言：
- ①`thumbs_contract_test` 断言 `makeThumbnails` 内有 `catch` + `unlink`
- ②`layout_contract_test` 断言 backfill 路径有 `finally` 包 `unlink`
- ③`queue_contract_test` 断言前端处理 `contended`

### 3.2 第二批：修正确性与规模化瓶颈

#### ④ 内存预检改为批内基线快照

不要每张图都读 `memory_get_usage(true)`，改为**批开始时快照一次**，
批内按同一基线判定：

```php
// processQueue 循环外，认领成功后：
$memBaseline = memory_get_usage(true);
// decodeWouldExceedMemory 改收一个 $baseline 参数
```

更彻底的方案：GD 资源在 PHP 8 是**对象**由引用计数回收，
`imagedestroy()` 实为 no-op，实际上批内峰值是**必然发生**的。
所以关键是——**基线应该反映"批内已经用掉多少"**，
而不是让每张图都从"已经用掉的峰值"再减一次。

用批初快照后：一批 10 张大图仍可能被误判，但**至少与顺序无关**，
且第一次判断一定是最宽松的。真正的根治是给解码设独立子进程或按图调
`memory_limit`，但那是更大的改动。

#### ⑤ 生成列 + 复合索引（消除 2 次全表回表）

```sql
ALTER TABLE images
  ADD COLUMN thumb_meta VARCHAR(16)
    GENERATED ALWAYS AS (COALESCE(JSON_UNQUOTE(JSON_EXTRACT(
      IF(JSON_VALID(processing_state), processing_state), '$.thumb_meta'
    )), 'pending')) STORED,
  ADD INDEX idx_status_meta (process_status, thumb_meta);
```

这条改动收益很大：
- `:1029`/`:1032` 的两条 COUNT 变成覆盖索引扫描
- 顺带**加速 backfill 的选行查询**（`:1157`），那才是补全工具的性能瓶颈
- 对 10 万行表，加索引约几秒；生成列 STORED 会重建表（需评估停机窗口）

> ⚠️ 这是**破坏性 DDL**（STORED 生成列会重建表）。建议：
> 先加普通索引 `idx_process_status` 已存在的前提下，只加生成列；
> 或用 VIRTUAL 生成列 + 显式索引（不重建表，但需每次访问时计算）。

#### ⑥ 8 次 COUNT 合并为 2 次

```sql
-- 一条 GROUP BY 拿到全部状态计数（走覆盖索引）
SELECT process_status, COUNT(*) FROM images GROUP BY process_status
```

```sql
-- 一条 SUM(CASE) 拿到两个 JSON 分支计数
SELECT
  SUM(process_status='done' AND <thumbMetaPendingSql>)    AS no_thumb,
  SUM(process_status='done' AND <thumbMetaRetryableSql>) AS meta_retryable
FROM images
```

**8 → 2**，且第 1 条是覆盖索引扫描，成本远低于现在。

#### ⑦ 批次上限提到 50–100

5 处硬编码改为一处定义 + 引用。考虑到 `set_time_limit(120)`
（`:716`），建议**提到 50 而不是 100**——避免大批次撞超时导致整批重来。

| 改动 | 位置 | 收益 |

## 4. 架构级建议（单独立项）

### 后台 worker

当前"浏览器即 worker"是**唯一无法靠调参解决的量级限制**。
三条路：

| 方案 | 改动量 | 适用场景 |
|---|---|---|
| **A. CLI 常驻脚本** | 小（复用现有 `backfill-thumbs-batch.php` 的构造 Request 技巧） | 宝塔环境，用 Supervisor 保活 |
| **B. cron 批处理** | 最小 | 低频（每 5 分钟跑一次即可消化日常积压） |
| **C. 真队列** | 大（需 Redis/RabbitMQ） | 当前规模**不必要** |

**推荐 A**：`src/cli/process-queue.php`，参照现有
`backfill-thumbs-batch.php:36-42` 的做法（伪造带 CSRF 的 Request、
构造控制器、调 `processQueue()`）——**零逻辑重复**，
因为所有处理逻辑都在控制器里。

Web 前端的轮询入口保留（上传后即时反馈体验好），但不再是唯一消费者。
两个入口靠现有的条件 UPDATE 认领天然互斥，无需额外协调。

> ⚠️ 但要注意：CLI 与 Web 同时跑时，CLI 也会触发那 8 次 COUNT。
> **建议先做 ⑥（合并 COUNT），再做 worker**——否则多个 worker 各自全表扫描，
> 反而更糟。

## 5. 执行顺序建议

```
第一批（P0，可立即做）        ①临时文件自清理  ②backfill finally  ③前端退避
                              ↓ 各自独立、互不影响，约 3 处小改
第二批（正确性+规模）         ④内存基线快照  ⑤生成列索引  ⑥合并COUNT  ⑦批次上限
                              ↓ ⑤需评估停机窗口，建议单独执行
第三批（整洁度）              驱动复用  显式列  抽公共方法
                              ↓
架构（独立立项）               CLI worker（务必在 ⑥ 之后）
```
