### 2026-09-21 · 响应收敛为「请求什么图就返回什么」（5 项关闭 / 1 项待环境放行）

- **实现**（工作区，未打包）：`ApiController::imagePayload()` 改为**单地址** `url`（= 按 `size` 解析后那张）
  + 极短的 `size`（如实回报实际生效尺寸）；`random` / `list` 的缺省统一为 `SIZE_ORIGINAL`。
- **★ 连带的关键推导**：`url` 现在承载「请求的那张图」，所以缺省**必须**是 `original` ——
  若仍是 `md`，不传 `size` 的既有调用方会从「拿到原图」变成「拿到缩略图」，那才是真正的破坏性变更。
- **元数据同主体**：`width`/`height` 对缩略图由 `Image::thumbDimensions()` 推导；`mime_type` 从缩略图键
  扩展名推导（不写死 `image/webp`，认不出报 `null` 而不猜）；`file_size` 缩略图为 `null`（字节数未入库，
  不为它多打一次对象存储往返 —— 正解是生成时入库，属独立立项）。
- **单一来源**：`thumbDimensions()` 由**生成端与读取端共用**（此前生成端自己算 `$scale`），
  消灭「接口报的宽高」与「实际生成的图」两套规则。
- **删除**：`Image::thumbUrls()`（全库 0 调用方）。
- **契约测试**：`api_contract` 45 → **66 项**（§3/§5/§7 重写）；`thumbs_contract` 50 项同步
  （`thumbUrls` 断言翻转为「必须不存在」、不放大守卫改指向 `thumbDimensions`、API 载荷断言换成单地址）。
- **未完成（OPEN）**：`docs.php` 与 §7 的两条断言 —— 该文件读取被环境连续拦截。
  **因此未打包、不可部署**（部署包里的文档页会宣传已移除的字段）。

### 2026-09-21（当日第三批）· 缩略图字节数「读不到」时的重试策略 — 待拍板

**问题**：`StorageInterface::size()` 返回 `null` 时（对象不存在 / CDN 分块传输无 `Content-Length` /
网络抖动 / 签名失效），当前 `encodeThumbBytes` 恒写 `{"ok":1}` → 该行**离开待补全集合** →
那一档 `file_size` 永久为 `null`，再点「补全缩略图」也不会重试。

**三个方案（用户要求解释，已给出对比图）**：

| 方案 | 机制 | 优点 | 代价 |
|---|---|---|---|
| A 保持现状 | 恒写标记，行离开集合 | 队列必然前进；`file_size: null` 是已语义化的「未知」，**不谎报** | 「测不到的那档」永久为 null，需手工重置才重试 |
| B 全测到才写 | 有档位失败就不写标记 | 自动重试 | **已证伪**：行留在集合 → `remaining` 永不归零 → 前端**无限循环**（无轮次上限），每轮空打对象存储；且坏行 ≥ batch 时队头占位 |
| C 加尝试次数 | 写标记 + 记次数，行离开集合 | 前进不阻塞，且可定向重试/可诊断 | 多一列（schema + 自迁移 + 判据变复杂） |

**另提一个 D（免 schema 的轻量变体）**：`encodeThumbBytes` 在 JSON 里多记一个失败档数组
（如 `{"ok":1,"sm":18432,"__missing":["lg"]}`）——行为等同 A（不阻塞），但**可诊断**且可
**一键重置**（`UPDATE images SET thumb_bytes='' WHERE thumb_bytes LIKE '%\"__missing\"%'`），
修好环境后能全量重试。改动量约 3 行。

**★ 本轮发现（推翻我先前的推荐）**：我此前说「B 改 1 行、倾向 B」，是**错的** ——
B 必须同时改「前端加轮次上限」或「选行加游标」才安全，否则是无限循环。
**结论修正为：A 是安全基线；要更好就用 D；要做完整就用 C。**

**另一个方向（消除失败而非管理失败）**：若 `null` 主要来自「CDN 不给 `Content-Length`」，
正解是给 `sizeUrl()` 加降级路径（`Content-Length` 缺失时改发 `Range: bytes=0-0` 读
`Content-Range`，或退化为流式计数），从源头消掉这类失败 —— 与选哪个方案无关，可独立做。

### 2026-09-22 · 缩略图元数据「读不到」的重试策略 —— 选 C，载体改为通用状态列

- **用户裁定**：选 **C**，但把载体从"尝试次数列"改为**「图片处理状态」总控列** —— 状态是语义化的
  （能区分"没测到"与"本来就不需要"），计数只是数字。另定：5 值状态机、队列页加重试按钮。
- **实现**：`images.processing_state JSON`（按处理项分键，如 `{"thumb_meta":"partial"}`）——
  将来新增处理项只需加键，不必再加列；**键缺失 = 未处理** ⇒ **存量行无需停机回填**。
- **两难的结构性解法**：状态列把「未处理」与「处理过但失败」分开 ⇒ 失败行**离开队列**（不阻塞）
  却**仍可被定向重试**。retry 用**扫描游标**（`from`/`next_from`）推进 —— 因为失败行重试后状态仍是
  `failed`，按判据重选会每轮取到同一批（这正是 B 方案被证伪的原因）。
- **零网络快速路径**：`thumbs` 与 `thumb_bytes` 都已完整的行只需一次纯 DB 推导就登记 `ok`，
  不下载不解码 —— 这是"加列不用停机回填"能成立的原因，且顺带自愈历史不一致。
- **硬失败刻意不写状态**（保持 `pending` 以便自动重试），与"读到长度失败"（写 `failed`，等人工重试）
  有意区分。
- **契约测试**：`thumbs_contract` 71 → **118 项**（新增 §9）；**14 向故障注入全部命中**。
  其中两处**最初漏网**并已修正断言：
  ① `$fillable` 断言用 `[\s\S]*?` **跨全文匹配**，fillable 之外出现同名字样就照样通过
  （改为一律**只看 fillable 数组内部**）—— 漏的恰是本项目的 P0 场景；
  ② 快速路径的"无 I/O"断言起点取在 `if ($derived …)`，而注入的 `resolveProfile()` 在它之前
  （起点改到该段落的注释处，并把 `resolveProfile(` 纳入禁止模式）。
- **顺带发现**：分类页两个死按钮（见上表新增的 OPEN 条）。
