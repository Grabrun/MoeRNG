## 1. 背景与问题

随机图 API（`/api/v1/random`）是本站对外的主要接口。它的 JSON 一直返回 `thumb`（md）与
`thumbs`{sm,md,lg}，但**没有"直接取缩略图"的能力**：

- `type=redirect` 只能 302 到**原图** —— 想省流量的调用方（列表页、缩略图墙）拿不到小图；
- 没有尺寸参数，`thumb` 固定 `md`，无法按场景选 320/640/1280；
- `/api/v1/images` 同样如此，而它才是缩略图的最大消费者（一次返回一页）。

三个缺口叠加的现实后果：调用方只能拿原图自己做缩放 —— 流量与首屏时间都由调用方承担。

同时存在若干**约束**（勘察阶段确认，不是假设）：

| 约束 | 内容 |
|---|---|
| 已有线上用法 | `?type=redirect` 被当作「原图直出」使用，已有第三方引用 |
| 尺寸可用性不齐 | sm/lg 是**懒生成**的，历史图片可能只有 md（需跑后台「补全历史缩略图」） |
| URL 有时效 | 本地 `/files` 走 HMAC 签名（`signed_ttl` 默认 300s），云端走预签名直链，同样有时效 |
| 架构原则 | 云端一律**预签名直链、不经过源站**（源站不代理字节） |
| API 定位 | 只读、高并发、被限流；已有独立的后台批量工具承担所有写操作 |

---

## 2. 决策

**给现有端点加 `size` 参数，不新增端点。**

```
GET /api/v1/random?size=sm                      → JSON，thumb 取 320px
GET /api/v1/random?type=redirect&size=sm        → 302 → sm 缩略图
GET /api/v1/images?limit=20&size=sm             → 列表每项 thumb 取 320px
```

| 行为 | 规则 |
|---|---|
| 取值 | `sm`(320) / `md`(640) / `lg`(1280) / `original`（原图） |
| **缺省值** | **一律 `original`**（原图）。统一缺省不是「保守」，而是必需：`url` 承载「请求的那张图」，缺省若是 `md`，不传 `size` 的既有调用方会从原图变成缩略图（**2026-09-21 修订**，原为按端点区分） |
| 白名单来源 | `Image::THUMB_SIZES` 的键 + API 侧 `SIZE_ORIGINAL` 常量（**不硬编码**） |
| 非法值 | `400` + 列出合法取值（**不静默回退**） |
| 尺寸未生成 | 兜底链 `请求尺寸 → md → 原图`，**绝不 404** |
| 实际生效尺寸 | 新增极短的 **`size`** 字段**如实回报**（回退过就写回退后的值，回退到原图写 `original`） |
| 响应载荷 | **只有一个地址字段 `url`**，且 `width`/`height`/`mime_type`/`file_size` **全部描述 `url` 指向的那一张图**（2026-09-21 修订，此前附带 `thumb`/`thumbs`/`thumb_size` 三件套） |
| 缓存 | `/random` 两个分支均 `no-store`；`/images` 用 `private, max-age=30` |

---

## 3. 红线（不可违反）

> 红线 = 违反后会造成**线上破坏性后果**的约束。每一条都绑定了契约断言与故障注入，
> 改坏会立刻变红，而不是等到线上报障。

### 红线 1 — 兼容性：`type=redirect` 不传 `size` 时**必须仍指原图**

| 项 | 内容 |
|---|---|
| 为什么是红线 | 线上已有调用方按「原图直出」用它。把缺省值改成 `md` 会**静默改变所有既有调用的语义** —— 对它们而言是"图片突然变小"，且没有任何报错 |
| 违反的后果 | 破坏性变更（静默降级）：第三方拿到的图变小/变糊，排查成本极高（对方不会想到是服务端改了默认值） |
| 如何锁死 | `api_contract_test.js` §3：断言**两端点缺省都是 `SIZE_ORIGINAL`**，且**不得存在**按 `type` 区分缺省的三元（前者防回退静默，后者防有人「优化」成 md 缺省）。§5 另断言 `url` 取自解析结果 |
| 正确的改法 | 若要改缺省，必须**开新端点或新版本路径**（如 `/api/v2/random`），不得原地改缺省 |

### 红线 2 — 缓存：`/random` 的 `no-store` 必须设在**分支之前**，覆盖 JSON 与 redirect 两条路径

| 项 | 内容 |
|---|---|
| 为什么是红线 | `/random` 的 URL 是**固定**的，语义却是「每次换一张」。一旦被缓存，**缓存时长直接等于随机失效时长** —— 用户刷新 100 次拿到的还是同一张 |
| 违反的后果 | 随机功能整体失效（不是性能问题，是功能问题）；且症状极隐蔽（浏览器不回源，看起来"有时正常"） |
| 为什么必须在分支之前 | 该端点有 JSON 与 redirect 两条路径。设在 redirect 分支内，JSON 路径就裸奔 —— **实施时就真的这样漏过一次** |
| 如何锁死 | `api_contract_test.js` §6：断言 `header('Cache-Control: no-store, max-age=0')` 的位置**早于** `if ($returnType === 'redirect')`，并做故障注入（挪进分支 → 立刻红） |
| 正确的改法 | `no-store` 是**功能性**要求，不是保守起见，不要为了"省限流"去掉；想省限流应引导调用方用 `/api/v1/images?limit=N` 一次取一批 |

## 4. 配套不变量（同样不可违反）

| # | 不变量 | 理由 | 锁在哪 |
|---|---|---|---|
| I1 | 兜底链**只此一处实现**：`Image::displayUrlWithSize()`；`displayUrl()` 只做委托 | 两处实现迟早演化出两套行为（"视图里能回退、API 里不能"这类不一致极难发现） | §4：断言委托关系 + 链顺序 `请求尺寸 → md → 原图` **不可颠倒** |
| I2 | 尺寸白名单**必须取自 `THUMB_SIZES`**，函数体内不得出现硬编码尺寸名 | 尺寸表是单一来源；硬编码会在增删尺寸时静默漏掉 | §1：断言判定用 `isset(Image::THUMB_SIZES[$raw])` 且体内无 `'sm'`/`'md'`/`'lg'` |
| I3 | **不谎报尺寸**：`size` 报实际生效值（回退到原图写 `original`） | 没有它，请求 `sm` 而该档未生成时会静默回退到 md/原图，调用方无从察觉 | §5：断言 `'size' => $actual` 且 `$actual = $resolved['size'] ?? self::SIZE_ORIGINAL` |
| I4 | 两端点**共用** `imagePayload()` | 字段漂移（只有一处新增字段）是接口最常见的退化方式 | §5：断言 random 与 list 都调用同一载荷函数 |
| I5 | 在线测试页的 URL 展示与实际请求**同源**（`buildApiPath()` 唯一拼装点） | 测试页的价值是"所见即所测"；两处各写一遍会漂移，反而把人带偏 | §8：断言 `new URLSearchParams()` 在 `initApiTester` 内恰好一次、`/api/v1/random` 只出现一处 |
| I6 | **响应里所有字段描述同一张图**（`url` 指向的那张）：单地址、无缩略图映射 | 字段属于不同主体时，调用方按 `width` 预留布局会偏（2560 的框里放 320 的图），且不报错 | §5：断言不含 `thumb`/`thumbs`/`thumb_size`，元数据取自该图的推导 |
| I7 | **缩略图尺寸推导只有一份实现**（`Image::thumbDimensions()`）：生成端与读取端共用 | 两处各算一套，「接口报的宽高」与「实际生成的图」迟早对不上，且不会报错 | §5 与 `thumbs_contract` §5：断言生成端调用它、且不再自己算 `$scale` |

## 5. 被拒方案（及理由）

| 方案 | 拒绝理由 |
|---|---|
| 新增 `GET /api/v1/thumb` 端点 | 语义与 `/random?type=redirect` 完全重叠。多一个端点 = 多一处维护 + 多一套文档 + 多一份契约测试 |
| `type=proxy`（源站代理图片字节以支持长缓存） | 与「云端预签名直链、不经过源站」的既有架构原则**直接冲突**，且烧源站带宽与 CPU。需要长缓存应配 CDN 域名，而不是让 API 当图床 |
| API 按需生成缺失的缩略图尺寸 | 给只读、高并发、被限流的入口加写路径（GD 解码 + 上传），风险不对等；补齐仍走后台「补全历史缩略图」 |
| 非法 `size` 静默回退成 `md` | 调用方会以为拿到了指定尺寸 —— 与 I3 冲突。宁可 400 让人早发现 |
| 给 `/random` 加 `max-age` 以省限流 | 见红线 2：会杀死随机本身 |
| 下调 `signed_ttl` 默认值 / 改为固定域名 | 默认值本身没问题，问题在**使用者不知道 URL 有时效**。改为在文档页讲清时效与"不要长期存库" |

## 6. 后果

**正面**

- 列表页/缩略图墙可以直接取小图，流量与首屏时间由"原图"降到"320px 级"。
- 缺省值按端点区分 → **零破坏性变更**：既有 `?type=redirect` 行为一字未改。
- 尺寸缺失不再导致调用方炸（兜底链），且 `thumb_size` 让"实际拿到什么"可被程序判断。
- 缩略图**文件本身**的缓存已由既有机制承担（本地 `/files` 为 `private, max-age=60`，云端由对象存储/CDN 控制），重复请求不打源站。

**负面 / 需接受**

- 调用方需理解「缺省值按端点不同」这条规则（已在 API 文档页参数表与红线 1 中显式写明）。
- 干跑式的"候选 ≠ 必然更小"这类如实类语义同样适用于缩略图：`thumbs` 只含**真实存在**的尺寸，
  缺失的要靠兜底链 —— 调用方不能假设 `size=lg` 一定拿得到 1280。

**中性**

- URL 时效性（`signed_ttl` 默认 300s）保持不变；文档新增「返回 URL 的时效性」一节。

## 8. 回顾触发条件（何时重新审视本决策）

出现以下任一情况时应重开本 ADR（并在 `OPEN-DECISIONS.md` 登记）：

1. 需要**真正的图片处理能力**（任意尺寸/格式协商、裁剪、水印）—— 那是独立的图像服务，不是本接口的延伸；
2. 站点上下行流量成本**主要由 API 直出承担** —— 应改配 CDN 域名，而非放宽缓存；
3. 缩略图从"懒生成"改为"上传即全尺寸生成" —— I2/I3 的兜底链语义可重新评估；
4. 出现 `/api/v2` —— 红线 1 的缺省值约束在新版本路径上可以重新决定。

## 附：术语

| 术语 | 含义 |
|---|---|
| `size` | 请求的图片尺寸：`sm`/`md`/`lg`/`original` |
| `thumb` | 响应中**按 `size` 解析后**的那一个缩略图地址 |
| `thumbs` | 响应中**真实存在**的全部尺寸映射（可能不含请求的尺寸） |
| `thumb_size` | 实际生效的尺寸（回退时为回退后的值） |
| 兜底链 | `请求尺寸 → md → 原图`，保证"有图就绝不 404" |

## 9. 修订记录（Amendments）

### 2026-09-21 · 响应收敛为「请求什么图就返回什么」

**触发**：用户看到 JSON 响应里带着 `thumb` + `thumbs`（3 个签名 URL，各约 450 字节）——
请求一张图却收到一串候选，对调用方是纯负担。

**口径**：不给 `original` 开特例，一律**按请求的 `size` 返回那一张**；响应里**所有字段都描述这一张**。

| 改动 | 前 | 后 |
|---|---|---|
| 载荷字段 | `url`（恒为原图）+ `thumb` + `thumbs` + `thumb_size` | **`url`（= 按 `size` 解析后那张）** + `size` |
| 缺省 `size` | 按端点区分（JSON = `md` / redirect = `original`） | **一律 `original`**（否则 `url` 会从原图变缩略图 = 破坏性） |
| `width`/`height` | 原图尺寸 | **该图的尺寸**（缩略图由 `Image::thumbDimensions()` 推导，与生成端同源） |
| `mime_type` | 原图 mime | 该图的 mime（缩略图从键扩展名推导，认不出报 `null` 而不猜） |
| `file_size` | 原图字节数 | 原图时给值；**缩略图为 `null`**（字节数未入库，不为它多打一次对象存储往返） |
| `Image::thumbUrls()` | 供 API 使用 | **删除**（载荷移除后全库 0 调用方） |

**红线 1 的形态随之变化**（内容不变、判据更严）：原判据是「缺省由端点决定」，现为
**「两端点缺省都必须是 `original`，且不得存在按 `type` 区分缺省的分支」** —— 因为 `url` 现在承载
「请求的那张图」，缺省一旦混用就会静默改变既有调用方的 `url` 语义。

**新增不变量**：I6（单地址、字段同主体）、I7（尺寸推导单一来源）。

**已知取舍**：`file_size` 对缩略图为 `null`。若将来确实需要，正解是**生成缩略图时把字节数一并入库**
（一次 schema 变更 + 回填），而不是在读取端为每张图打一次 HEAD 请求。
